# Liked-songs archive automation — design

## Problem

Today, building a "Digital Archive #NNN" playlist is a manual weekly chore:
like songs on Spotify, watch the count, hand-create a playlist once 30
accumulate, hand-move the tracks in, then run `npm run build-archives` to
refresh the site. This spec automates everything except liking songs
themselves.

## Constraints and decisions

- **Liked Songs is never pruned.** Pedro keeps every song liked forever —
  including ones already archived — so that re-encountering an old song
  later shows it as already liked, preventing accidental duplicate
  archiving. This rules out "whatever's still liked is pending" as a
  tracking strategy.
- **Archive order is oldest-liked-first (FIFO).** If more than 30 pending
  songs exist at once, the oldest ones are archived and the newest remain
  pending for a future run. (Confirmed via Pedro's own worked example:
  "count down the 5 newest, then the next 30 belong in an archive" is
  mathematically the same as "archive the oldest 30 of the pending set.")
- **The repo is public**, and Pedro explicitly chose to accept that a
  pending-songs ledger will be committed and publicly visible before
  those songs are sealed into an archive — same tradeoff the site already
  makes for sealed archives, just slightly earlier in the lifecycle.
- **New archive playlists must match existing ones**: named
  `Digital Archive #NNN`, public, non-collaborative (verified against all
  29 existing archive playlists on Pedro's account).
- **Archive #29 is currently open** (22/30 tracks) — the automation must
  be able to top off an in-progress archive, not just create full ones
  atomically.
- **Weekly execution is a Claude scheduled cloud agent**, not GitHub
  Actions — Pedro wants Claude itself checking in weekly and reporting
  back, not silent CI.

## Architecture

Extends the existing `digital-archives` repo, following its current
patterns: small `scripts/lib/*.mjs` modules, dependency-injected `run()`
functions for testability, `vitest` unit tests, `dotenv`-loaded
credentials, `npm run <script>` entry points.

### Source-of-truth split

- **Archived tracks**: the union of track IDs across
  `public/data/archive-*.json` — already the canonical per-archive record,
  already regenerated by `build-archives` on every run. No separate
  bookkeeping duplicates this.
- **Pending tracks**: a new committed ledger,
  `scripts/state/liked-songs-queue.json`. Holds only tracks that are
  liked but not yet confirmed archived, each with the metadata needed to
  add them to a playlist (`id`, `name`, `artists`, `addedAt`, `uri`).
  Sorted oldest-first by `addedAt`.

The ledger exists for two reasons: it lets each run page Liked Songs only
until it reaches a track it's already seen (bounded, incremental sync
instead of re-fetching the whole library every week), and it gives a
durable, human-readable record of "what's coming" independent of
Spotify's live, ever-growing Liked Songs list.

### New Spotify API surface (`scripts/lib/spotify-api.mjs`)

- `fetchLikedSongs(token, { until, fetchImpl })` — pages `/me/tracks`
  (newest-first, Spotify's default order), stopping early once a track ID
  in `until` (a Set of already-known IDs) is encountered.
- `createPlaylist(token, userId, name, { fetchImpl })` — POST
  `/users/{user_id}/playlists`, `public: true`, `collaborative: false`.
- `addTracksToPlaylist(token, playlistId, uris, { fetchImpl })` — POST
  `/playlists/{playlist_id}/tracks`, chunked at Spotify's 100-URI-per-call
  limit.

`scripts/lib/spotify-client.mjs`'s `spotifyFetch` gains an options
parameter for HTTP method and JSON body (currently GET-only).

### Ledger sync (`scripts/lib/liked-songs-queue.mjs`)

Pure functions, unit-testable without network:

- `syncQueue(queue, likedSongs)` — appends any liked song not already in
  the queue (dedup by ID), preserving `addedAt` order.
- `pruneArchived(queue, archivedTrackIds)` — removes queue entries whose
  ID now appears in `archivedTrackIds` (safety net for tracks archived
  outside this automation, e.g. a manual playlist edit).
- `planFill(queue, openArchive)` — given the current open archive's
  playlist ID and its existing track count (0-29), and the pending queue,
  returns a plan: `{ topOff: [...trackIds up to 30 total], newArchives: [
  {trackIds: [...30]}, ... ], remaining: [...still pending] }`. Only ever
  batches in exact groups of 30 for *new* archives; top-off can be a
  partial batch since it's continuing an already-open archive.

### Orchestration (`scripts/archive-liked-songs.mjs`, → `npm run
archive-liked-songs`)

Same `run({ token, ...injected deps, log })` shape as `build-archives.mjs`:

1. Load the ledger; fetch archived-track-ID set from
   `public/data/archive-*.json`.
2. `fetchLikedSongs` incrementally (stop at first already-known track).
3. `syncQueue`, then `pruneArchived`.
4. Determine the current open archive (highest `#NNN`; open if <30
   tracks per its playlist, per a fresh `fetchPlaylistTracks` call — not
   the possibly-stale local JSON, so a rerun after a partial prior
   failure self-corrects against Spotify's real state).
5. `planFill`, then execute: `addTracksToPlaylist` for the top-off (if
   any pending exist), `createPlaylist` + `addTracksToPlaylist` for each
   full new archive batch.
6. Re-run the existing archive-fetch-and-write logic (reused from
   `build-archives.mjs`) to regenerate `public/data/*.json`.
7. Write the pruned ledger (remaining pending only) to
   `scripts/state/liked-songs-queue.json`.
8. Report a summary: tracks synced, archives topped off/created, tracks
   moved, pending count left over.

Nothing is committed by the script itself — the calling agent (or a
human) commits `public/data/*.json` plus
`scripts/state/liked-songs-queue.json` together, exactly as the
`sync-digital-archives` skill already does for the read-only sync.

### Weekly trigger

A Claude scheduled cloud agent (via the `schedule` skill), configured
after the script is built and manually verified once. Prompt runs `npm
run archive-liked-songs`, commits + pushes if anything changed, and
messages Pedro with a summary — including surfacing (not retrying) any
Spotify auth failure, per the existing `sync-digital-archives` skill's
guidance not to attempt re-authorization autonomously.

## Error handling

- Any Spotify API failure (expired/revoked token, exhausted rate-limit
  retries, unexpected response shape) aborts the run before any commit —
  no partial state is pushed.
- Playlist creation is idempotent against Spotify's live state: the "next
  archive number" and "is it open" are computed by querying Spotify
  fresh each run, not trusted from the ledger or local JSON, so a rerun
  after a crash mid-way (e.g. playlist created, tracks not yet added)
  naturally continues rather than double-creating a playlist.

## Testing

Unit tests (mocked Spotify responses, matching the existing
`build-archives`/`spotify-api` test style) for:

- `syncQueue` / `pruneArchived` — append-new, dedupe, and prune-on-archive
  behavior.
- `planFill` — top-off-only, top-off-then-one-new-archive,
  top-off-then-multiple-new-archives, and remainder-stays-pending cases,
  including the 30-cap boundary.
- `spotify-api.mjs` additions — pagination + early-stop for
  `fetchLikedSongs`, chunking for `addTracksToPlaylist`.

## Out of scope

- Un-liking songs (explicitly rejected — Liked Songs is permanent).
- Placing new playlists into the "digital archives" folder (not exposed
  by the Spotify Web API; Pedro will drag them in by hand if he wants
  that).
- GitHub Actions or any non-Claude trigger.
